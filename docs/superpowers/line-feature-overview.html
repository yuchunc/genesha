Ganesha — LINE Chat Interface Feature Overview

A LINE Official Account that quietly listens in the teacher's student group and doubles as her private AI assistant — answering questions from ledger data and proposing draft records that only become real once she taps confirm.

⚠ Designed, not yet built — implementation plan has 19 tasks, all unchecked

1

Scope

One LINE Official Account, two surfaces, one shared agent engine underneath.

In scope

  • The bot sits in the teacher's existing student group, listening only — it never sends a message into the group.
  • The same account, reachable by the teacher 1:1, acts as a conversational AI assistant that can answer questions from ledger data and propose draft records for her to confirm.
  • One unified AI agent (tool-calling loop) powers both surfaces — no separate regex parser, no separate "extraction-only" code path.
  • Drafts (payment, attendance, makeup) proposed by the agent from either surface, confirmed or discarded inline via quick-reply/postback in the teacher's LINE 1:1 chat. Nothing the agent produces becomes a real ledger fact without that explicit human tap.

Explicitly out of scope (deferred)

  • A student-facing chat experience — noted for a later phase; the group thread never sends outbound messages to students under this design.
  • LIFF, ID-token login, or any new end-user (student) authentication surface.
  • Automated payment reconciliation (ECPay or otherwise) — unaffected finding carried over unchanged from the original ledger spec.
  • Multi-tenant support.

Architecture at a glance

Every inbound LINE event takes the same path in; where it goes after that depends on who sent it.

LINE Platform → POST /line/webhook
Public route on its own pipeline (not :browser or :api). Raw bytes are cached, the x-line-signature header is checked against Base64(HMAC-SHA256(channel_secret, raw_body)), then the event is deduped by webhook_event_id, persisted as a LineEvent, and the request gets a 200 — nothing else happens inline.
▼ Oban job (decouples the 2s webhook ack from LLM latency)
Ganesha.Assistant.ProcessEventWorker
Routes by source.type and sender: a group event goes to the group thread; a 1:1 event from the configured teacher LINE user id goes to the teacher thread; anything else (unknown 1:1 sender, room, …) is ignored and the event is just marked processed.
▼ one shared engine, reused for both threads
Ganesha.Assistant.Agent
Loads thread history + system prompt, then runs a tool-calling loop (capped iterations) against Ganesha.Assistant.Provider (an adapter behaviour); tool calls dispatch to Read / Draft / Reply tools.
Group thread
Silent — no send tool
The Reply tool is not registered at all for this thread. The only output is any drafts created plus updated thread memory — the bot never posts into the group.
Teacher's 1:1 thread
Replies + draft confirm
Reply tool registered. Text reply sent via LINE's Reply API (Push fallback if the reply token expired). A created draft arrives as a quick-reply template with 確認 / 修改 / 捨棄 actions.
▼ postback tap → same POST /line/webhook
Apply or discard — existing context functions, not new writes
Sales.record_payment/1 + Sales.confirm_payment/2, Roster.create_attendance/1, or Roster.book_makeup/3 — the same functions a human action in the app already calls.
Async via Oban, not a hand-rolled supervisor. Oban.Engines.Lite is already configured and running Ganesha.Reporting.CloseMonthWorker in production, so reusing it here gets retry/backoff for free now that "processing an event" can mean an LLM call that fails or times out, not a pure function.

Data model summary

Four new tables — none of them exist yet in priv/repo/migrations/.

line_events

Every raw inbound LINE webhook event, deduped by webhook_event_id — the source of truth before any processing happens.

webhook_event_id · source_type · source_id · raw_type · payload · processed_at

assistant_threads

One row per conversation — the group thread or the teacher's 1:1 thread — keyed by source type and id.

source_type ("group" | "teacher") · source_id

assistant_messages

The conversation history replayed to the LLM provider on every turn; group-thread content is purged at 24h.

thread_id · role ("user" | "assistant" | "tool") · content · tool_calls

drafts

Structured proposals (payment / attendance / makeup) the agent creates — never a real ledger fact until a human taps confirm.

thread_id · kind · student_id · parsed · confidence · state · applied_record_type/id
4

Draft lifecycle

The same shape for every draft kind, whichever thread proposed it:

  • Propose — a draft tool (propose_payment_draft, propose_attendance_draft, propose_makeup_draft) inserts a drafts row in state: "pending". Draft tools only ever insert into the drafts table — they never call a state-mutating context function directly.
  • Confirm surface — in the teacher's 1:1 thread, the reply carries a LINE quick-reply template with three actions: 確認 (confirm) / 修改 (edit) / 捨棄 (discard).
  • 確認 → apply — the postback tap flips the draft to state: "applied" and dispatches to the matching context function: Sales.record_payment/1 + Sales.confirm_payment/2 for a payment draft, Roster.create_attendance/1 for attendance, or Roster.book_makeup/3 for a makeup request.
  • 修改 → edit — opens the existing app's draft/edit surface, not a new LINE-side editing flow; she edits the record the same way she would today, then confirms there.
  • 捨棄 → discard — the postback tap flips the draft to state: "discarded". No ledger row is ever created.
The core trust guarantee: nothing the agent produces becomes a real ledger fact without an explicit human tap. This postback confirm is the same human confirmation action already required by the ledger's payment-trust invariant — architecturally identical to tapping confirm in the app UI, just over a different transport. No code path may set payment.state = "confirmed" outside Sales.confirm_payment/2.
5

Retention & safety guardrails

  • Group-thread raw text purges at 24h — line_events.payload and assistant_messages.content sourced from group input.
  • Two things are exempt from that purge: drafts.parsed (structured, not raw text — a draft older than 24h keeps its parsed fields but loses the sentence that produced it) and the teacher's own 1:1 thread, which is retained indefinitely as a deliberate design decision (functionally equivalent to her typing a note into the app).
  • No group member roster is ever stored, matching the disclosure-notice requirement carried over from the original onboarding runbook.
  • The group thread structurally can never call the LINE send API — enforced in code, not by a prompt: no Reply/send tool is registered for the group thread's tool set, and the group branch of the worker never even references the LINE client. A successful prompt-injection attempt via a student's message is bounded to "creates a spurious draft she rejects" — never a real ledger or messaging side effect.
  • Tool-call iteration cap of 6 calls per agent run, on both threads, bounding cost and latency against adversarial or rambling input.
  • Only the configured teacher LINE user id gets the teacher thread's privileged tool set (the Reply tool, and is treated as a trusted principal); any other 1:1 sender is ignored, not silently given assistant access.
Flagged, not settled: whether the teacher-thread's indefinite retention counts as "Friend/Group information" under LINE's User Data Policy is unverified — LINE does not define that boundary. If a legal review disagrees, adding a purge job for the teacher thread is a one-line change.
